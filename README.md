# Description

The goal of this project is to build an autonomous **Code Agent** capable of solving complex programming tasks without human intervention. Instead of relying on static prompts, the agent implements a dynamic **Thought → Code → Observation** reasoning loop.

The system interacts directly with a Large Language Model (LLM) and executes model-generated code within a secure, isolated **Sandbox**.

Tool integration is powered by the **Model Context Protocol (MCP)**:
- The MCP server exposes a suite of specialized tools (file system inspection, code search, execution, and test evaluation) as standardized Python functions.
- The sandbox dynamically discovers these tools and makes them callable directly from the code generated by the LLM.
- By observing execution outputs and error traces from the sandbox, the agent iteratively refines its code until it successfully passes all test cases (for **MBPP** algorithmic challenges) or produces a valid git patch (for real-world **SWE-bench** repositories inside Docker).

## System architecture

The framework is organized into modular layers with clear separation of concerns, decoupling orchestration, network communication, isolated execution, and external tool protocols:

### Core Components

1. **Agent Orchestrator (`src/agent/`) :**
   - Serves as the central state machine.
   - Parses benchmark input files (`MBPPTaskInput` / `SWEBenchTaskInput`).
   - Tracks per-step performance data (`StepMetrics`), enforces iteration and token budgets, and formats the final `solution.json`.

2. **LLM Provider Layer (`src/llm/`) :**
   - Implements multi-token management and resilient provider fallback (e.g., Gemini → OpenRouter → Groq).
   - Automatically switches API keys or alternative models upon encountering rate limits (HTTP 429) or endpoint errors.
   - Encapsulates responses into a structured `LlmResponse` object, extracting raw code, latency (`request_time_ms`), and usage telemetry (`prompt_tokens`, `completion_tokens`).

3. **Execution Sandbox (`src/sandbox/`) :**
   - Acts as the security boundary between LLM-generated code and the host environment.
   - Executes untrusted code inside an isolated child process with strictly constrained memory and system built-ins.

4. **Model Context Protocol Layer (`src/mcp/` & root servers) :**
   - Provides external capabilities through independent servers communicating via JSON-RPC 2.0 over standard I/O or HTTP.
   - Tools are dynamically discovered and converted into native Python function calls within the sandbox namespace, allowing the agent to inspect files, search codebases, and run evaluation scripts without exposing host privileges.

## Agent loop explanation

The autonomous agent is driven by an iterative **Thought → Code → Observation** cycle. Because Large Language Models are inherently stateless (having no memory between distinct API calls), the orchestrator maintains full conversation provenance across turns to enable multi-step reasoning, test-driven iteration, and self-correction.

```
       ┌────────────────────────────────────────────────────────┐
       │                                                        │
       ▼                                                        │
┌──────────────┐        ┌──────────────────┐        ┌───────────┴────────┐
│   THOUGHT    │ ────►  │       CODE       │ ────►  │    OBSERVATION     │
│  LLM Reasons │        │ LLM Writes Code  │        │ Executed in Sandbox│
└──────────────┘        └──────────────────┘        └───────────┬────────┘
                                                                │
                                                                │ (Passes / final_answer)
                                                                ▼
                                                        ┌────────────────┐
                                                        │  FINAL ANSWER  │
                                                        │ SolutionOutput │
                                                        └────────────────┘
```

The loop operates through the following steps:

1. **Prompt Construction & Memory Management:**
   - On the first turn, the agent initializes the conversation with a system prompt detailing available MCP tools, execution rules, and task constraints (`task_definition`, function signature, assertions).
   - In subsequent iterations, the full history of the conversation is preserved by alternating roles (`user` → `assistant` → `user`). The model receives its previously generated code followed by the sandbox's actual execution feedback.

2. **Code Extraction:**
   - The LLM's response is received via the provider fallback cascade.
   - The parser inspects the raw output and cleanly isolates executable Python code from markdown code fences (` ```python ... ``` `).

3. **Sandboxed Execution & Observation:**
   - The extracted code is dispatched to the isolated sandbox.
   - The sandbox executes the code against candidate tests or MCP tool calls and captures all standard output (`stdout`), standard error (`stderr`), and exceptions (`AssertionError`, syntax errors, timeouts).

4. **Feedback & Termination Conditions:**
   - **Case A (Self-Correction):** If execution fails or an assertion fails, the detailed traceback and returned output are appended as a new `user` message with explicit correction instructions. The LLM re-analyzes its logic, updates its hypothesis, and attempts a new fix.
   - **Case B (Success):** When all assertions pass, the LLM calls the built-in `final_answer(solution_code)` function. The sandbox intercepts this call, terminates the loop, and outputs the validated solution.
   - **Case C (Limit Reached):** If the loop reaches `max_iterations` (10 for MBPP, 30 for SWE-bench) or exceeds token/time quotas, execution stops gracefully and logs a non-zero exit status or error in `SolutionOutput`.
## Sandbox design

The sandbox acts as a strict security and execution boundary designed to safely run untrusted code generated by the LLM without endangering the host system. It is implemented in standard Python without external sandboxing libraries, relying on four core defensive layers:

1. **Process Isolation (`multiprocessing`):**
   - Untrusted code is executed inside a dedicated child process spawned via `multiprocessing.Process`.
   - This prevents memory corruption, unhandled crashes, or `sys.exit()` calls from killing the primary agent orchestrator.
   - A strict wall-clock timeout (`max_execution_time_seconds`) is enforced by the parent process; runaway processes (e.g., infinite loops) are terminated immediately with `process.terminate()`.

2. **System & Resource Limits (`setrlimit`):**
   - Hard limits on physical memory usage (`RLIMIT_AS`) are enforced directly via the Linux kernel (`resource.setrlimit`), preventing denial-of-service via memory exhaustion (e.g., large array allocations).

3. **Restricted Built-ins & Namespace Sanitization:**
   - The execution namespace replaces standard Python `__builtins__` with a strictly vetted allowlist of safe built-in functions (`print`, `len`, `range`, math functions, standard exceptions).
   - Dangerous built-ins capable of privilege escalation or arbitrary file system access (`open`, `eval`, `exec`, `breakpoint`) are removed or guarded.

4. **Import Filtering (Allowlist Guard):**
   - The Python import mechanism (`__import__`) is overridden with a custom security guard.
   - Modules can only be loaded if explicitly present in the configurable `authorized_imports` allowlist (e.g., `math`, `re`, `collections`, `itertools`). Wildcard submodules (e.g., `math.*`) are supported. Any unauthorized import raises an `ImportError`.

5. **Tool Injection & Result Capture:**
   - Standard output and standard error are captured via `io.StringIO` and returned back to the agent loop along with execution status (`success`, `error`, `final_answer`).
   - The sandbox integrates a `final_answer(solution_code)` construct to signal task completion and dynamically exposes connected MCP tools directly inside the Python namespace.
